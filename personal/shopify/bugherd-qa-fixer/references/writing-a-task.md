# Writing a QA task an AI can fix

How to write a new BugHerd task on a Shopify theme so it can be picked up and fixed without a conversation.

**The task is the entire brief.** Whoever fixes it — a developer or an AI — cannot see your screen, does not know what you were doing, and will not guess. Anything you leave out either stalls the task or gets guessed wrong. A task that can't be reproduced is never fixed; it is sent back as a question, and that round-trip costs more than the thirty seconds it takes to write it properly.

Two rules carry most of the weight:

> **Say what is wrong, and say what right looks like.**
> **One defect per task.**

Everything below is detail on those.

---

## Anatomy of a fixable task

| | field | why it matters |
|---|---|---|
| 1 | **Title** | one short line, so the board is scannable |
| 2 | **Where** | pin on the element; the pin supplies URL, viewport, browser, screenshot |
| 3 | **Element, in words** | the pin's stored selector is theme-specific and does not survive to another theme |
| 4 | **Which build** | live, or the draft/preview link you used — the URL alone does not record this |
| 5 | **State** | anything that isn't logged-out, default country, empty cart |
| 6 | **Actual** | what you see |
| 7 | **Expected** | what it should be — a value, a design frame, or a sentence |
| 8 | **Severity** | so the batch can be ordered |
| 9 | **Evidence** | screenshot is automatic; add a video for anything that moves |

Fields 6 and 7 are the ones people skip. They are the task.

---

## 1. Pin it on the element

The pin is not decoration — it is what gives the task its page URL, window size, browser, OS, screenshot, and the element you clicked. A task filed without a pin arrives with none of that and is unactionable on arrival.

If the thing you want to report can't be pinned — it only appears on hover, it's inside a modal that closes, it's the whole page — pin the nearest stable element and say in words what you actually mean, or use the template at the bottom.

## 2. Name the element in words as well

Add three or four words: *"the price under the Add to Cart button"*, *"the second card in the collection grid"*, *"the newsletter field in the footer"*.

Two reasons. The pin can land slightly outside the element you meant. And the CSS path it stores contains ids generated by the specific theme you were looking at — those change on a duplicated or draft theme, so the stored path can end up matching nothing where the fix is actually made. Your words survive that; the selector doesn't.

## 3. Say which build you were on

**A URL does not record the theme.** The live site and a preview of a draft theme produce identical-looking URLs on the same page. Two tasks with the same URL can be about completely different code.

- On the live site → write **live**.
- On a preview or draft link → **paste the link you clicked**.
- Preview links expire — a shareable visitor preview lasts about **2 days**, a merchant preview about **30**. If you're re-opening a link from earlier in the week, it may have quietly dropped you back onto the live site.

## 4. State anything that isn't the default

The fixer opens the page cold: logged out, default country and currency, empty cart, nothing selected, no scrolling. If your bug needs more than that, it will not reproduce.

Name it if any of these applied:

- logged into an account
- items already in the cart
- a specific variant, size, or swatch selected
- a specific country, currency, or language
- a dropdown, modal, drawer, or accordion open
- you had scrolled, hovered, or clicked something first

## 5. Write both halves: actual **and** expected

"Wrong" is not a specification. Every task needs both sides.

| ❌ not fixable | ✅ fixable |
|---|---|
| `padding is off` | `Gap above this section is ~120px. Should be 64px.` |
| `text too big` | `Heading renders at 40px. Design has it at 28px.` |
| `looks broken on mobile` | `At 390px wide the two cards overlap instead of stacking.` |
| `wrong colour` | `Button background is #4A90D9. Should be #1B2A4A.` |
| `these should be links` | `The three logos in this row aren't clickable. Each should link to its publisher's site.` |
| `fix the alignment` | `Prices sit at the top of each card. They should align to the bottom edge, like the first card.` |

You don't always need a number. There are exactly three valid ways to say what "correct" is:

**a. An exact value** — `16px`, `#1B2A4A`, `2 lines maximum`, `left-aligned`.

**b. A design reference** — a link to the specific frame, **with the node-id in it**. In Figma, right-click the frame → *Copy link to selection*. A link to the whole file is not enough; it can't be resolved to the frame you mean. Say which breakpoint the frame is for.

**c. A plain sentence describing the correct behaviour** — *"Clicking a logo should open that publisher's site in a new tab."* Fine for behaviour, not enough for anything visual.

If you can't supply one of these three, you don't yet have a task — you have an observation. File it anyway if you like, but mark it as a question rather than a defect.

## 6. One defect per task

If your description contains "and also", "plus", or a second sentence about a different thing, split it.

> ❌ *"This line is too thin, and the logos aren't centred, and they get cut off at the edge."*
>
> ✅ Three tasks.

Bundling means the task can't be closed until all of them are done, and nobody can tell which part is outstanding. Split tasks also get fixed faster, because they can be worked in parallel.

## 7. Report the symptom, not the fix

*"Change the padding to 20px"* tells the fixer what to type, not what's broken. Very often the real cause is somewhere else and the requested change either hides it or breaks another page that shares the same component.

Describe what you see and what it should look like. If you have a hunch about the cause, add it on a separate line as a hint — *"(might be the same problem as the collection page?)"* — not as the instruction.

## 8. Set a severity

Even a rough one. Without it, every task is treated as equally urgent, which means none of them are.

- **critical** — blocks buying, or the page is unusable
- **important** — clearly wrong on a page that matters
- **normal** — the default
- **minor** — cosmetic, low-traffic, or nice-to-have

## 9. Record motion as video

Anything intermittent, animated, hover-triggered, scroll-triggered, or carousel-related needs a recording. A still frame of a moving problem proves nothing and usually can't be reproduced from the screenshot alone.

## Extras by report type

| type | add this |
|---|---|
| **Doesn't match the design** | Figma frame link **with node-id**, and which breakpoint it is |
| **Layout / spacing** | the window width you saw it at; whether it also happens at other widths |
| **Mobile** | file it **from** a phone or a resized window — the recorded width is the width it gets checked at |
| **Something is missing** | say whether it's missing everywhere or only on this one page/product |
| **Broken interaction** | the exact steps, in order, and what should have happened at the end |
| **Wrong price / currency / language** | the country you switched to, the currency shown, and the currency expected |
| **Third-party app widget** (reviews, bundles, subscriptions, popups) | name the app if you know it — these are fixed differently from theme code |
| **Slow / janky** | which page, on what connection, and what specifically felt slow |

## Template

For anything you can't pin, paste this into the description:

```
Page:        <full URL, including any ?query>
Build:       live  |  draft/preview (paste the link)
Viewport:    <window width in px>  ·  desktop / mobile
State:       logged out / logged in · country · variant · anything opened first

Actual:      <what you see>
Expected:    <a value, a Figma frame link with node-id, or a sentence>
Element:     <a few words naming it>
Steps:       1. …  2. …  3. …
```

---

## Before you submit — the self-check

Read your task back and answer these. Any "no" is a round-trip.

- [ ] Is it pinned, or does it carry a full URL?
- [ ] Have I named the element in plain words?
- [ ] Have I said which build — live or a preview link?
- [ ] Does it say what's wrong **and** what right looks like?
- [ ] If it's a design mismatch, is there a frame link with a node-id?
- [ ] Is it exactly one defect?
- [ ] Have I named any non-default state?
- [ ] If it moves, is there a video?
- [ ] Is severity set?

---

## What makes a task unfixable

These come back as questions, every time:

- no pin and no URL
- a symptom with no statement of what's correct
- "doesn't match the design" with no frame link
- two or more defects in one task
- a state-dependent bug with the state unnamed
- a mobile report filed from a desktop window
- a screenshot with no words — the image shows *what*, never *what should be*
- a fix instruction with no symptom behind it
